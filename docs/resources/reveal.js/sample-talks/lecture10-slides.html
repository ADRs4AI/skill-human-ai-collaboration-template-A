The algorithm in two lines:
Match? counter++  ·  Mismatch? counter−−  ·  Zero? switch candidate
One pass · O(1) space · Deterministic
What MJRTY guarantees:
If a strict majority (>50%) exists → MJRTY finds it. Always. Regardless of stream order.
What it doesn't guarantee:
If no majority exists → output is arbitrary. MJRTY can't tell the difference. You need verification.
Today: Two distinct limitations → two distinct solutions

The Missing Property

"Fails Gracefully" — Why It's the Hardest

MJRTY has two very different behaviors:
  • Majority exists → MJRTY always outputs the majority element. Guaranteed.
  • No majority → MJRTY outputs some candidate, but it might be completely arbitrary.
The algorithm cannot tell these cases apart.
It always produces a candidate. The caller must verify.
Why metaphors miss this:
Stories have protagonists who "win." The hero slays the dragon. The strongest survives. These narratives imply a meaningful victor — but MJRTY's victor may be meaningless.
Why the Flagpole gets it right:
A flag always flies after the last soldier — but the mechanism never claims it's the winner. The uncertainty is built into the structure.
Model sentence: "…but if no army had a true majority, the flag flying at the end is whoever outlasted the others — not necessarily the largest force."
Key pedagogical moment. MJRTY is correct BY DESIGN: it gives a CANDIDATE, not a PROOF. The algorithm's contract: "if a majority exists, I find it; if not, I give you someone, no promises." The Flagpole is honest because the mechanism never claims the flag is the winner.

Activity 1 — 12 min

Modify MJRTY to Find Top-2

The challenge: Design an algorithm to find both elements with frequency >33%.
  • Fixed number of variables (no unbounded storage)
  • One pass through the stream
  • Must handle: matches candidate 1, matches candidate 2, matches neither
The tricky part: What happens when an element matches neither candidate?
This is the key insight. Think carefully.

Work with your neighbor:

  • You'll need 2 candidates + 2 counters
  • Element matches candidate1 → ?
  • Element matches candidate2 → ?
  • Element matches neither → ?

MJRTY in StreamLang (starting point):

let cand: Element = read(); let cnt: Count = 1; while (hasNext()) { let x: Element = read(); if (equal(x,cand)==1) { cnt=cnt+1; } else { cnt=cnt-1; } if (cnt==0) { cand=x; cnt=1; } } return cand;
Circulate. The key insight is: when element matches NEITHER candidate, it "fights" BOTH candidates simultaneously — both counters decrement. This is not obvious. Students who figured it out from the challenge card should be asked to share without giving away the answer.

The Pattern

The Generalized Algorithm

// Two candidates, two counters let c1, c2: Element // candidates let k1, k2: Count = 0 // counters for each element x in stream: if x == c1: k1++ else if x == c2: k2++ else: // matches neither k1-- // ← the key insight: k2-- // fight BOTH simultaneously if k1 == 0: c1 = x; k1 = 1 if k2 == 0: c2 = x; k2 = 1 return {c1, c2} // candidates, not guarantees
The insight: When an element matches neither candidate, it "fights" both simultaneously — one from each camp is eliminated.
Why this works: If an element appears >1/3 of the time, it can't be completely cancelled by all the others combined.
O(1) space · One pass · Deterministic
Same properties as MJRTY, now for k=3 icebergs.
Walk through the ELSE case slowly. "This is the insight: a non-matching element fights both candidates simultaneously — like it defeats one representative from each." Then ask: "Can you generalize this to k-1 counters for any k?"

How to verify a candidate without storing the stream?
Recall from Tuesday's Activity 3:
Hoeffding's inequality tells us: sample ~600 elements, count how many are the candidate, and get 95% confidence.

The hard part: How do we get 600 uniformly random samples from a stream we can't store?

Before the Answer

How would you take a random sample from a stream?

slido.com/5020
Open text poll: "How would you take a 10% random sample from a live stream?"
No wrong answers — we're exploring intuitions.
Read answers aloud. Common ones: "flip coin each time with 10% probability" (variable sample size!), "take every 10th element" (not random — adversary can exploit pattern), "store all then sample" (defeats the whole point). All wrong for specific reasons — surface those reasons before presenting the solution.
The Challenge

Why Naive Approaches Break

❌ Flip a coin (10% chance each element)
Sample size varies randomly: sometimes 8%, sometimes 12%. Hoeffding needs exactly m samples for its guarantee.
❌ Take every 10th element
Not random — it's deterministic and periodic. An adversarial stream can place all interesting events between sampled positions.
❌ Store all, then sample
Defeats the entire purpose. Stream is too large to store (that's why we're here).
What we actually need:
  • ✓ Exactly m samples (not approximately)
  • ✓ Uniform probability (every element equal chance)
  • ✓ Works online (can't look backward)
  • ✓ O(m) space (not O(N))
All four constraints together seem impossible.
They're not.
Let the impossibility land. Then: "There's an algorithm from 1981 — the same year as MJRTY — that solves this exactly. It's called reservoir sampling."
The Solution

Reservoir Sampling (Knuth, 1981)

// Keep m elements in the reservoir let reservoir: Array[m] for each (i, x) in stream: if i ≤ m: reservoir[i] = x // fill first m else: j = random(1, i) // uniform in [1..i] if j ≤ m: reservoir[j] = x // replace: prob m/i return reservoir // uniform, |reservoir| = m
Guarantee: after n elements, every element has probability m/n of being in the reservoir — uniform, exactly m samples.
Trace (m=3, stream A B C D E):
i=1[A, ·, ·]fill
i=2[A, B, ·]fill
i=3[A, B, C]fill
i=4j=rand(1,4)if j≤3: swap
i=5j=rand(1,5)if j≤3: swap
Fisher-Yates / Knuth shuffle:
Reservoir sampling is the streaming version of the classic random shuffle — uniformity by random replacement.
Walk through the trace. The key question: why does this give uniform probability? Prove by induction: after n elements, each element has probability m/n (Challenge Card 2A). At i=n: each element either survived from before or replaced in the last step. The math works out elegantly.

Putting It Together

Problem 1 Solved: Full Verification

Run simultaneously in one pass:
  1. MJRTY → finds candidate c       (O(1) space)
  2. Reservoir sampling → collects m=600 samples   (O(m) space)
  3. After the pass: count c in the reservoir
  4. Hoeffding → 95% confidence answer
Total: O(N) time · O(m) space · one pass
No second pass needed. No stream stored. Statistically guaranteed.
Why does this work?
MJRTY and reservoir sampling are independent — one reads each element to update the candidate, the other decides whether to include it in the reservoir. They can run in the same loop.
This is what Cloudflare, AWS Shield actually do.
DDoS candidate identified by Boyer-Moore; verified by sampling-based count; Hoeffding gives the confidence bound for the firewall decision.
"This answers the question from Tuesday: 'How do we verify without storing traffic?' You sample DURING the same pass MJRTY is running. The insight: two algorithms can share one stream." Let that land.

Challenge A  ·  Analysis

Prove Reservoir Sampling is Uniform

Claim: After processing n elements, each element has probability m/n of being in the reservoir.

Prove by induction on n.
Base case: n = m (first m elements → probability 1).
Inductive step: element i has probability m/i; show it's m/n after all n.
