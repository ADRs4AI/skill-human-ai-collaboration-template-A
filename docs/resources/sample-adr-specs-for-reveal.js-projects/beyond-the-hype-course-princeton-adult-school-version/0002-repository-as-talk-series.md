**The key insight you're articulating:**
- The *content* (topic stacks, frameworks, research) is **stable and reusable**
- The *delivery* (which stacks, in which order, for which questions) is **instance-specific**
- The *record* (what happened, what worked) is **session-specific and archival**

These three concerns should be separated in the repo structure.

---

## AI Interpretation

**The mental model that fits:**

This is essentially a **curriculum platform** with:
1. A **library** of topic stacks (the "marketplace") — grows over time, gets better with each session
2. A **session builder** — assembles stacks for a specific delivery, given audience + submitted questions
3. A **session archive** — records what actually happened (slides used, questions asked, transcript, debrief)

The library is where value compounds. Each session teaches you something about which stacks work, which framings land, what questions audiences actually ask. That feeds back into improving the library.

## Alternative: Simpler First Step

Rather than a full restructure now, a **minimal viable migration**:

1. Create `topics/` with one README.md per topic (just text, no slides yet)
2. Create `sessions/2026-02-27-princeton-adult-school/` and move the session artifacts there
3. Leave `slides/` as is, pointing to existing HTML files
4. Revisit the "slides as composable snippets" question after 2-3 more sessions

This preserves what's working while building toward the library model.

## What This Architecture Enables

Once established:

| Goal | How the architecture supports it |
|------|----------------------------------|
| Bring talk "on the road" | Each session reads from the same topic library; new session = new config file |
| Improve a topic between sessions | Update `topics/labor-automation/README.md`; regenerate slides when needed |
| See what questions come up most | Grep pre-class questions across all sessions |
| Track what stacks you actually used | Session README.md records the actual selection |
| Give a 30-min vs 2-hour version | Different session configs selecting from the same library |
| Have an AI build the next session | Provide: topic library + submitted questions → AI generates session slides |

## Doubts / Generative Friction

NOT: **The library model assumes topics are stable.** They might not be. "Labor & automation" content will look different in 2027 than 2026. How do you want to handle versioning within a topic? Update in place? Branch?

NOT: **The "session as archive" model has a packaging question.** If the slides reference CDN resources, the archived session deck won't work offline in 5 years. Should sessions archive a self-contained copy with embedded CSS/JS?

NOT: **The "meta marketplace" idea is powerful — but how does it manifest?** Is it a slide deck (index-meta.html), a web page, a printed catalog, a Markdown document? The form affects how you actually use it when planning a new session.

NOT: **You mentioned "bringing it on the road."** Different venues will have different constraints (Zoom vs. in-person, 30 min vs. 2 hrs, experts vs. general public). Should the session README.md capture audience metadata systematically so you can search across sessions for patterns?
